## 初步确认的问题

### 问题 1：求购成色字段前后端与数据库 schema 不一致

当前前端求购发布页使用：

```js
wantedConditionList: ['不限', '全新', '99新及以上', '95新及以上', '90新及以上', '85新及以上', '80新及以上']
```

后端 `CreateWantedDTO` 也新增了校验：

```java
@Pattern(regexp = "^(全新|99新及以上|95新及以上|90新及以上|85新及以上|80新及以上)$")
private String conditionLevel;
```

但是数据库脚本 `backend/db/schema.sql` 中 `wanted.condition_level` 仍然是旧枚举：

```sql
condition_level ENUM('全新','99新','95新','9成新','八成新','八成新以下')
```

这会导致发布或编辑求购时，如果选择 `99新及以上`、`95新及以上` 等新值，后端校验通过，但数据库写入失败。

可能表现：

- 软件端发布求购失败
- 编辑求购失败
- 后端返回 500
- 控制台出现类似 `Data truncated for column 'condition_level'` 或 enum 值不合法的错误

建议修复：

1. 把 `wanted.condition_level` 从旧 ENUM 改成 `VARCHAR(50)`，或更新 ENUM 为新值。
2. 对已有数据库提供升级 SQL。
3. 同步检查 `schema.sql`、实际本地数据库、前端选项、后端 DTO 校验四处是否一致。

推荐 SQL：

```sql
ALTER TABLE wanted
MODIFY condition_level VARCHAR(50) DEFAULT NULL COMMENT '期望成色';
```

### 问题 2：聊天会话列表隐藏了没有消息的会话

当前 `ChatService.listMySessions` 新增了过滤：

```java
.isNotNull(ChatSession::getLastMessage)
```

如果用户从商品详情或求购详情创建了会话，但还没有发送第一条消息，这个会话会被消息列表隐藏。

可能表现：

- 点击联系后进入聊天页，但返回消息列表看不到会话。
- 新会话看起来像没有创建成功。

需要确认产品期望：

- 如果希望只展示有消息的会话，可以保留。
- 如果希望“创建会话后就能在消息列表看到”，需要移除该过滤，或创建会话时写入一条系统消息/初始化 lastMessage。

### 问题 3：聊天页发送商品卡片时读取了对方的商品列表

当前 `frontend/pages/chat/chat.vue` 中商品选择器使用：

```js
getUserItems(this.partnerId || this.userId, { status: 'ON_SALE' })
```

如果“发送商品”是发送自己的商品卡片，那么这里应该读取当前登录用户 `this.userId` 的商品，而不是对方 `partnerId` 的商品。

可能表现：

- 聊天里点“商品”时显示的是对方商品。
- 自己无法选择自己的在售商品发送。

建议修复：

```js
getUserItems(this.userId, { status: 'ON_SALE' })
```

### 问题 4：求购详情进入聊天时没有把 wantedId 传给聊天页

当前 `frontend/pages/wanted-detail/wanted-detail.vue` 创建会话后跳转：

```js
uni.navigateTo({ url: '/pages/chat/chat?id=' + session.id + ... })
```

但 `chat.vue` 新增的关联求购条依赖：

```js
options.wantedId
```

商品详情已经传了 `itemId`，求购详情没有传 `wantedId`。

可能表现：

- 从求购详情进入聊天页时顶部不显示关联求购条。

建议修复：

```js
uni.navigateTo({
  url: '/pages/chat/chat?id=' + session.id
    + '&partnerId=' + (pid || 0)
    + '&name=' + encodeURIComponent(this.detail.username || '')
    + '&avatar=' + encodeURIComponent(session.partnerAvatar || '')
    + '&wantedId=' + this.detail.id
})
```

### 问题 5：商品详情创建会话失败后的 fallback 跳转可能使用了错误 id

当前 `frontend/pages/goods-detail/goods-detail.vue` 中：

```js
catch (e) {
  uni.navigateTo({ url: '/pages/chat/chat?id=' + this.goodsId })
}
```

`chat.vue` 的 `id` 是聊天会话 ID，不是商品 ID。这里把商品 ID 当成会话 ID，会导致聊天页加载错误会话或空消息。

建议修复：

- 创建会话失败时不要跳转到聊天页。
- 改为显示错误提示。

### 问题 6：前端与后台接口地址都硬编码为 127.0.0.1:8080

当前：

```text
frontend/api/index.js
frontend/api/chat.js
frontend/api/item.js
frontend/api/user.js
admin/api/request.js
```

都存在硬编码：

```js
http://127.0.0.1:8080
```

如果在浏览器 H5 且后端运行在同一台电脑，通常可以工作。

如果在手机、小程序模拟器、局域网其他设备、组员电脑或不同端口运行，就可能请求不到后端。

建议修复：

- 抽统一配置文件，例如 `frontend/api/config.js` 和 `admin/api/config.js`
- 文档中明确本地 H5 使用 `127.0.0.1:8080`
- 小程序/真机调试时改成电脑局域网 IP

## 2026-06-07 补充：软件端举报后台无消息

### 现象

软件端当前举报入口在 `frontend/pages/profile/profile.vue` 的右上角更多操作中，进入 `frontend/pages/report/report.vue` 后会调用 `POST /api/reports` 创建举报。数据库中能看到 `report` 记录，但后台管理端举报列表 `GET /api/admin/reports` 返回 500，导致后台看起来“没有任何消息”。

### 根因

当前软件端举报是“只举报用户”的记录，只会带 `reporterId`、`targetUserId`、`reason`、`description`、`imageUrls`。`itemId`、`wantedId`、`orderId`、`chatSessionId`、`handlerId` 等关联字段可能为空。

后台 `AdminReportService.enrich` 在补充举报列表展示字段时，对这些空关联字段直接调用 `Map.of(...).get(null)`，Java 不允许 `Map.of()` 生成的不可变 Map 使用 null key，因此触发 `NullPointerException`，接口返回 500。

### 已修复

1. `backend/src/main/java/com/yatidle/backend/service/AdminReportService.java`
   - 增加 null-safe 查询辅助方法。
   - 举报列表和详情补充用户名、商品、求购、订单信息时，允许关联字段为空。
   - 软件端“只举报用户”的记录现在可以正常返回给后台。

2. `backend/src/test/java/com/yatidle/backend/service/AdminManagementServiceTest.java`
   - 新增 `listReportsReturnsUserOnlyReportFromFrontend` 回归测试。
   - 覆盖软件端举报用户、不带商品/求购/订单关联字段的场景。

3. `backend/src/main/java/com/yatidle/backend/common/exception/GlobalExceptionHandler.java`
   - 对未捕获异常增加日志输出，后续后台或软件端遇到 500 时可以直接从后端日志定位堆栈。

## 2026-06-07 补充：后台举报处理与软件端功能同步迭代计划

### 当前问题总结

1. 举报详情图片显示问题
   - `admin/pages/reports/reports.vue` 的举报截图只使用普通 `image-list + uni.previewImage`。
   - `admin/pages/items/items.vue` 的商品详情已经有更完整的大图查看器、`object-fit: contain` 兼容样式、上一张/下一张切换和关闭逻辑。
   - 计划：举报详情图片展示参考商品详情实现，补独立图片查看器和 Web 端图片容器样式。

2. 举报处理缺少“一键恢复”闭环
   - 当前 `AdminReportService.handle` 支持 `BAN_USER` 和 `OFFLINE_ITEM`。
   - `BAN_USER` 会调用 `AdminUserService.updateStatus(..., "inactive", ...)`，用户封禁后会联动下架该用户在售商品，并关闭该用户开放求购。
   - 用户管理页单独解封用户时，只恢复用户状态，不会恢复此前联动下架的商品/求购。
   - 当前举报管理页也没有恢复按钮，管理员不能在举报上下文里一键恢复被封禁用户及其商品/求购。
   - 计划：新增明确的恢复动作，支持从举报页恢复封禁用户，并同步恢复该用户因封禁被下架/关闭的内容。

3. “下架商品”的恢复范围需要明确
   - 用户希望：如果举报处理动作是“下架商品”，点击恢复时恢复相关商品；如果是“封禁用户”，点击恢复时同时解封用户并恢复他的商品。
   - 文案里提到“把它的所有商品恢复”，实现时建议分两类：
     - 对 `BAN_USER` 的恢复：恢复该用户所有可恢复的下架商品和被关闭求购。
     - 对 `OFFLINE_ITEM` 的恢复：优先恢复举报关联商品；如果产品语义确认是“恢复被举报用户所有商品”，则后端方法可复用用户级恢复，但按钮文案必须写清楚。
   - 不建议无条件恢复已售、已删除或原本就由管理员单独下架的内容。

4. 用户管理 UI 状态不够直观
   - `admin/pages/items/items.vue` 对 `REMOVED` 商品有红色行背景和状态胶囊。
   - `admin/pages/users/users.vue` 当前只显示文本“正常/封禁”，没有行级颜色和状态胶囊。
   - 计划：用户管理页参考商品管理页，为 `inactive` 用户增加浅红背景/左侧色条，为正常用户显示绿色状态胶囊。

5. 软件端新功能与后台维护面的差距
   - 软件端已有举报、钱包、信用、收藏/求购收藏、通知、评价等页面。
   - 后台已有：举报、评价、订单、商品、求购、用户、聊天、分类、日志。
   - 需要同步维护：
     - 举报：补举报图片上传到后端，避免 `http://tmp/...` 或本地临时路径在后台无法稳定预览。
     - 用户：后台用户详情建议补余额、成交数、在售数、评价数等软件端信用页相关字段，便于客服判断账号状态。
     - 收藏/求购收藏：当前后台没有收藏管理页，暂时不是强必需，但可以在用户详情里加收藏数量作为运营信息。
     - 通知：软件端通知目前由订单列表聚合生成，不是独立通知表；后台暂不需要新增通知管理。
     - 钱包：软件端钱包余额来自 `GET /api/user/wallet`，交易流水由订单列表合成；后台可先在用户详情展示余额，不必立刻新增钱包流水管理。
